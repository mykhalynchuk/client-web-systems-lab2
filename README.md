# Лабораторна робота №2: Клієнтський застосунок управління бібліотекою

## Мета роботи
Розробити клієнтський застосунок для управління бібліотекою, який дозволяє вести облік книг та користувачів, а також виконувати операції з позичання та повернення книг із використанням TypeScript (класи, інтерфейси, generics, модулі, простори імен) та DOM API без використання декларативної розмітки в `index.html`.

---

## Контрольні питання та відповіді

### 1. Які переваги дає використання TypeScript порівняно зі звичайним JavaScript при розробці великого застосунку?
TypeScript додає сталу типізацію, що дозволяє виявляти помилки на етапі компіляції, а не в рантаймі. Він забезпечує кращу підтримку автодоповнення (IntelliSense) в середовищах розробки, полегшує рефакторинг та робить код самодокументованим і безпечнішим для підтримки великими командами.

### 2. У чому різниця між класом та інтерфейсом у TypeScript? Наведіть приклад, коли варто використати саме інтерфейс.
Клас — це сутність, яка містить як опис структури, так і реалізацію (логіку методів) і може створювати об'єкти (`new Book(...)`). Інтерфейс — це лише контракт (опис форми об'єкта або класу), який не генерує JavaScript-коду після компіляції. Інтерфейс доцільно використовувати для опису контрактів даних або пропсів, наприклад `IBook` чи `IUser`, коли потрібно гарантувати, що клас реалізує певний набір методів і властивостей.

### 3. Що таке Generics і навіщо вони використані саме в класі Library? Що було б втрачено, якби Library не був узагальненим (generic)?
Generics (узагальнення) дозволяють створювати компоненти, які можуть працювати з різними типами даних, зберігаючи сувору типізацію. У класі `Library<T>` це дозволяє керувати колекціями як книг, так і користувачів в одному універсальному класі без дублювання кодів. Якби `Library` не був узагальненим, довелося б використовувати тип `any`, що призвело б до втрати перевірки типів та потенційних помилок у рантаймі.

### 4. Поясніть різницю між модулями (ES-модулями) та просторами імен (namespaces) у TypeScript. Коли доречно використовувати namespace всередині модуля?
Модулі (`import`/`export`) працюють на рівні файлів і керують зовнішніми залежностями проєктів. Простори імен (`namespace`) — це інструмент TypeScript для логічного групування кодів всередині або між файлами у межах однієї глобальної області видимості. `namespace` доречно використовувати, наприклад, для організації груп чистих функцій валідації (`Validation.validateBookForm`), щоб не захаращувати глобальний простір імен окремими файлами для кожної дрібної перевірки.

### 5. Як організована модульна структура проєкту (models, services, utils)? Яку відповідальність несе кожен із цих шарів?
Архітектура поділена за шарами відповідальності:
- **`models/`**: містить сутності бізнес-логіки (`Book`, `User`) та їхні інтерфейси. Не знають про DOM чи UI.
- **`services/`**: містить бізнес-логіку керування станом колекцій (`Library<T>`) та взаємодію з `LocalStorage` (`Storage`).
- **`utils/`**: чисті допоміжні функції, генератори ID та валідатори (`Validation`).
- **`ui/`**: єдиний шар, який відповідає за рендеринг елементів через DOM API та взаємодію з користувачем.

### 6. Як реалізовано збереження та відновлення даних через клас Storage і LocalStorage? Які обмеження має LocalStorage як сховище даних?
Клас `Storage` використовує статичні методи `save` та `load`, які серіалізують об'єкти в JSON-рядок перед записом у браузерний `localStorage` і десеріалізують їх назад при завантаженні. Обмеження `LocalStorage`: невеликий обсяг пам'яті (зазвичай до 5–10 МБ), синхронність (може блокувати потік при великих обсягах даних) та збереження виключно рядкових даних.

### 7. Опишіть логіку методів позичання (borrow) та повернення (return) книги. Які стани книги вони змінюють і як це відображається в UI?
Метод `borrow(userId)` змінює статус книги (`borrowed = true`, `borrowedBy = userId`) та додає ID книги до списку позичених у користувача. Метод `returnBook()` скидає ці значення. В UI це динамічно змінює текст та варіант кнопки (з "Позичити" на "Повернути"), а також оновлює стан лімітів користувача.

### 8. Як реалізована валідація форм (обов'язкові поля, id користувача, рік видання)? Яким чином регулярний вираз перевіряє коректність року?
Валідація реалізована через простір імен `Validation`, який перевіряє заповненість полів та відповідність форматам. Для перевірки року використовується регулярний вираз `/^\d{4}$/`, який гарантує, що рядок складається рівно з 4 цифр.

### 9. Яке обмеження накладено на кількість одночасно позичених книг одним користувачем і як застосунок повідомляє про перевищення ліміту?
Користувач може одночасно позичити не більше 3 книг (`canBorrow()` перевіряє довжину масиву `borrowedBooks`). У разі спроби перевищити ліміт система блокує операцію та виводить модальне вікно з попередженням про помилку.

### 10. Чому в цій роботі заборонено писати декларативну розмітку в index.html, і як натомість генерується DOM-структура застосунку?
Це зроблено для глибокого вивчення програмного маніпулювання DOM за допомогою JavaScript/TypeScript. Усі елементи створюються динамічно в коді через метод `document.createElement`, налаштовуються їхні класи та події, після чого вони монтуються в єдиний контейнер `<div id="app"></div>`.

### 11. За Що відповідає vite.config.ts у проєкті? Назвіть щонайменше три ключові налаштування.
`vite.config.ts` відповідає за конфігурацію процесу збірки та локального сервера розробки (dev-сервер). Ключові налаштування:
1. `base`: базовий шлях для коректного деплою у підпапку на GitHub Pages.
2. Налаштування обробки TypeScript та стилів (Sass/Bootstrap).
3. Налаштування порту та параметрів швидкого гарячого оновлення модулів (HMR).

### 12. Яку роль виконують ESLint та Prettier у проєкті та в чому принципова різниця між їхніми задачами?
`ESLint` аналізує код на наявність логічних помилок, потенційних багів та порушень стандартів написання коду. `Prettier` відповідає виключно за форматування коду (відступи, лапки, крапки з комою), забезпечуючи єдиний стиль оформлення.

### 13. Що тестують юніт-тести для класів Library та Validation за допомогою Mocha? Наведіть приклад тест-кейсу для одного з методів.
Юніт-тести перевіряють ізольовану бізнес-логіку без участі UI. Наприклад, тест для перевірки пошуку у бібліотеці:
```typescript
it('should correctly search items using a predicate', () => {
    library.add(new DummyItem('1', 'Apple'));
    const results = library.search((item) => item.name.startsWith('A'));
    expect(results.length).to.equal(1);
});
```

### 14. Як працює Husky pre-commit hook у цьому проєкті і яку проблему він вирішує в командній розробці?
Husky перехоплює момент створення коміту (`pre-commit`) і автоматично запускає перевірки (наприклад, юніт-тести через Mocha). Якщо тести падають, Husky блокує створення коміту, що запобігає потраплянню непрацюючого або зламаного коду в репозиторій.

### 15. У чому основні відмінності між webpack та Vite за швидкістю запуску dev-сервера, налаштуванням конфігурації та розміром продакшн-збірки?
Vite значно виграє у webpack за швидкістю запуску dev-сервера (миттєвий старт завдяки використанню нативних ES-модулів браузера замість попередньої збірки всього бандлу) та простотою конфігурації (мінімалістичний `vite.config.ts` на кілька рядків). Продакшн-збірка Vite також відбувається швидше, використовуючи оптимізований Rollup під капотом.

## Висновок
Під час виконання лабораторної роботи було успішно розроблено клієнтський SPA-застосунок для управління бібліотекою з дотриманням принципів об'єктно-орієнтованого програмування, модульності та чистої архітектури.

У ході роботи було налаштовано збирач **Vite**, який продемонстрував високу швидкість запуску dev-сервера та зручність у конфігурації порівняно зі старими бандлерами. Завдяки використанню **DOM API**, весь інтерфейс застосунку генерується програмно. Надійність коду забезпечена строглою типізацією TypeScript, юніт-тестами на базі **Mocha та Chai**, а також автоматичним контролем якості через **ESLint, Prettier та Husky**. Проєкт повністю задеплоєно на GitHub Pages.
